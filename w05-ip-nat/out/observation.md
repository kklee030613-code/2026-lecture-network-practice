# Week 5 · Observation

## Task 1 · Subnets and longest-prefix match

- **/31과 /32:** `/32`는 호스트 하나뿐이라 `(addr, addr, addr)`를 돌려준다. 네트워크 주소와 브로드캐스트 주소를 따로 둘 공간이 없어 그 주소 자체가 유일한 호스트다(루프백, 라우터 ID에서 쓰는 방식). `/31`은 **RFC 3021**을 따라 두 주소 모두 호스트로 보고 `(net, net+1, net+1)`을 돌려준다. 점대점 링크에는 상대가 하나뿐이라 브로드캐스트가 필요 없고, 교과서식으로 "−2"를 하면 사용 가능한 주소가 0개가 되어 /31이 쓸모없어진다. 그래서 세 번째 값은 "브로드캐스트"가 아니라 마지막 주소다. `/30`부터는 일반 규칙을 따른다(10.0.0.0/30 → .1, .2, .3).
- **10.20.30.70이 매치한 항목:** `10.0.0.0/8`(campus), `10.20.0.0/16`(eng-building), `10.20.30.0/24`(lab-floor), `10.20.30.64/26`(lab-rack-2), 그리고 기본 경로 `0.0.0.0/0`까지 5개다. .70 = `01000110`의 상위 2비트 `01`이 .64/26의 `01`과 같다. 모두 "주소 AND 마스크 == 네트워크"를 만족하므로 매치 여부로는 승자를 고를 수 없다. **longest-prefix match** 규칙이 가장 구체적인 /26을 고르고, `/0`은 길이 0이라 어떤 매치에도 진다(R5).
- **같은 길이에 다른 next hop:** 같은 길이의 *서로 다른* 프리픽스는 겹칠 수 없으므로 한 주소에 둘이 동시에 매치되지 않는다. 충돌은 **같은 프리픽스를 두 번 add**할 때만 생기고, 테이블을 `(network, prefix_len)` 키의 dict로 두어 **나중 add가 앞의 것을 교체**하게 했다(`ip route replace`와 같은 동작). 그 밖에 `163.152.6.5/24`처럼 호스트 비트가 켜진 경우, 길이가 0–32 밖인 경우, 옥텟이 255를 넘는 경우는 `ValueError`로 거부한다. `ipaddress`와 `inet_aton` 없이 시프트와 마스크만 썼다.

## Task 2 · Where exactly are you? (자세한 내용은 `out/report.md`)

- **NAT 개수:** 유선은 사설 192.168.0.82/24 → 공인 121.153.38.57(KT)로 **NAT 1개**다. 근거는 traceroute 2번째 홉 121.153.38.1이 공인 주소와 같은 /24, 즉 공유기 WAN이 공인 주소를 직접 받는다는 점이다. 테더링은 172.20.10.2/28 → 118.235.88.99(KT 모바일)로 **NAT 2개로 판단**한다. iPhone NAT는 확실하고, 통신사 CGNAT는 출구 주소 대역과 iPhone 이후 홉이 전부 숨겨진 점으로 추론했다(iPhone의 셀룰러 IPv4가 10.x나 100.64/10이면 확정).
- **두 네트워크 비교:** 사설 주소, 마스크(/24 → /28), 게이트웨이, 공인 주소가 **전부 바뀌었다**. 사설 주소는 각 링크의 DHCP 서버(공유기 / iPhone)가 자기 대역에서 빌려준 것이고, 공인 주소는 마지막 NAT의 출구 주소이기 때문이다. 바뀌지 않은 것은 통신사(둘 다 AS4766 KT)와 노트북의 MAC뿐이다. 테더링에서는 전역 IPv6(2001:e60::)도 받았는데, 그 경로에는 NAT가 아예 없다.
- **Discover 출발지:** **0.0.0.0**이다(공식 trace frame #5, 목적지 255.255.255.255). 클라이언트는 아직 주소가 없고 그 주소를 받으려는 중이므로 다른 값을 쓸 수 없다. 서버 주소도 모르니 목적지는 브로드캐스트일 수밖에 없다. Offer와 ACK는 서버가 yiaddr를 정하고 chaddr로 MAC을 알게 된 뒤라 유니캐스트로 왔다. lease는 24 h이고, 절반(T1 = 12 h)에 유니캐스트로 갱신한다.

## Task 3 · Make longest-prefix match fast

```
baseline   lookup  12.080s        1,656 lookups/s
yours      lookup   0.009s    2,210,702 lookups/s   wrong 0   -> 1335x, strong
```
(실행마다 1,300–2,100×. baseline 자체가 PC 부하에 따라 6–15 s로 흔들린다.)

- **구조:** prefix-length 그룹화에서 한 단계 더 나간 **controlled prefix expansion**이다. 길이 17–24 프리픽스는 그것이 덮는 /24 슬롯들로, 1–16은 /16 슬롯들로 펼쳐 dict 두 개(`addr>>8`, `addr>>16`)에 넣는다. 25–32는 길이별 dict에, /0은 변수 하나에 둔다. 펼칠 때는 슬롯마다 채운 프리픽스의 길이를 기록해 **더 긴 프리픽스만 덮어쓰게** 했다. 이게 LPM을 빌드 시점으로 옮긴 것이다. **메모리 비용:** 5,000개 항목이 45,728개 슬롯(/24 쪽 13,553 + /16 쪽 32,175)으로 약 9배 늘었다. 길이 기록 dict까지 합치면 약 9만 개의 dict 엔트리다. /8 하나가 /16 슬롯 256개가 되므로 짧은 프리픽스가 많을수록 비싸진다. 1–24 전체를 /24 하나로 펼쳤다면 /8 한 개가 65,536칸이 되어 116개의 /8만으로 760만 칸이 필요했을 것이다. 그래서 두 단계로 나눴다.
- **R5 · lookup은 무엇에 비례하나:** 테이블 크기 N과 무관하게 **해시 probe 최대 2회 + (25–32 길이 그룹 수)**에 비례한다. 이 표에는 /25 이상이 없으므로 상수 2회다. baseline은 매 질의마다 N = 5,000개를 모두 비교하므로 O(N)이다. 그래서 속도 차이는 대략 N / 2에 Python 함수 호출 오버헤드를 더한 만큼이다. 30개 길이를 섞은 무작위 퍼즈 테스트(겹치는 프리픽스, 중복 add 포함, 9만 질의)에서도 LinearTable과 답이 모두 같았다.
- **왜 하드웨어는 bit-walk(trie)를 만드나:** 같은 표로 이진 trie를 만들어 재 보니 노드 52,862개, lookup 0.076 s로 해시 방식(0.008 s)보다 약 9배 느렸다. Python에서는 비트 하나마다 인터프리터 루프 한 바퀴, 리스트 인덱싱, 분기가 들어가 최대 32단계의 상수가 크다. 반면 dict 조회는 C로 구현된 한 번의 연산이다. 하드웨어 기준은 반대다. trie는 (1) **최악의 경우가 주소 폭(32단계)으로 결정적으로 고정**되고 해시 충돌이나 리사이즈가 없다. (2) 단계마다 고정 폭 메모리 읽기 한 번이라 **파이프라인으로 만들면 클록마다 패킷 하나**를 처리할 수 있다. (3) multibit trie로 단계 수를 조절하며 SRAM이나 TCAM에 맞춰 넣을 수 있다. 라우터에 필요한 것은 평균 속도가 아니라 **선로 속도에서의 최악 보장**이고, Python의 "빠른 답"은 인터프리터 오버헤드를 피하는 답일 뿐이다.
